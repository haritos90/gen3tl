Translation editor

Contributor guide

The editor changes the translation catalog of one game in one language: its texts, its glossary terms and the text pixels of its pictures. This guide explains writing and checking translations, exporting and submitting changes, and review before a release.

Quick start

  1. Open the Translation editor and choose the game and the Catalog language.
  2. Optional: give Your ROM, the original or a patched one. The editor then shows the English text and runs every check. The file stays in your browser.
  3. Open the editor. Find a text with the search or the filters and type its translation. The line meters show where a line is too wide for its window.
  4. Your changes stay in this browser as drafts; you can continue later.
  5. Press Submit. The page lists your drafts; add Notes for the reviewers if you wish.
  6. Press Open a GitHub issue with these changes; a GitHub account is needed. A long submission downloads as a JSON file: drag it into Export file on the form. Drag each downloaded picture into Pictures.
  7. Submit the issue. A check answers on it: a pull request with your changes, or the reason they were not applied. Correct the issue and the check runs again.
  8. A maintainer reviews the pull request. Approved changes enter a later version of the patch.

The sections below specify each step.

Requirements

  • A current browser with JavaScript and local storage. The check runs the toolkit's Python code in the browser with Pyodide, which the page loads from its CDN.
  • For a game's English text and exact ROM glyphs: the original base ROM, a published patched ROM, or a recognised base ROM together with its UPS patch. The ROM is optional for editing the keys and translations; the site interface needs no ROM.
  • For a submission through the editor, a GitHub account (see Submitting).

A game project’s catalogs are key-only: an entry’s msgctxt and msgid hold its stable key and msgstr its translation. The repository and the editor data hold keys, translations, states and measurements. The editor recovers the game’s English text locally from the verified ROM. Site-interface catalogs and draft source catalogs carry their own source text and need no ROM for it.

The ROM is read in the browser and stays local.

Opening the editor

The start screen of the editor offers a game and an optional ROM.

  1. Game. The games of the site, those at translation stage first.
  2. Your ROM, optional.

Open the editor opens the workspace.

Finding entries

With the ROM, the search matches English, translation or id; without it, translation or id. The filters:

FilterValues
StatusUntranslated; Translated: merged into the project and used in patches; Approved: confirmed by a reported playtest or by the review of the project; Nothing to translate: no English, such as an unused table slot; Edited here: a draft in this browser.
Check resultOverflowing, With errors, With warnings.
FileOne catalog file or a group of files.
MapThe maps where the text is used.
Window kindDialogue, Battle, Multi-line, Single line, Fixed field.
ReachReachable, Possibly reachable, Never shown: whether the game shows the text.
TermsShortened term: the entry shows the short label of a term.
Sort entriesStory order or File order.

Story order puts shown map files in the profile's map-name order, then system files, tables, other shown categories and battle entries; Never shown entries come last. File order follows the catalog. Changing the order retains the selected entry, its draft and the list scroll; filters, search and marks do not change.

A list row shows the status, the id, the window kind and the marks edited, overflow, errors, warnings, never shown and shortened. The keys are listed in Keys.

Writing the translation

The field edits the catalog text as units: characters, breaks and tokens. A break or a token is inserted and deleted whole. A backslash cannot be typed, so a break is inserted only by a key or a button above the field.

BreakMarkKeyEffect
\n↵EnterLine break.
\l⤓Alt+EnterScrolling line break: the box scrolls to show the next line, so a box with \l may hold more lines than the window shows.
\p¶Shift+EnterNew box.

In dialogue and battle boxes Enter inserts \n for the first break of a box and \l for every later one; in other windows it inserts \n.

Tokens: the chips above the field list the tokens of the English. A click inserts one at the caret; a chip is marked while the translation lacks it. A placeholder is text the game inserts, such as the player's name; a control code has no width, such as a text colour; a symbol is a named byte or a key icon. A token the character map does not know is reported by the check.

Pasted text keeps the breaks and tokens it writes as \n, \l, \p and braces; a real newline becomes \n. Copying puts the catalog form on the clipboard. Where the game shows the version of the translation, the text holds the token @VERSION@, which the check replaces with the release version.

Ctrl+Z undoes; Ctrl+Shift+Z or Ctrl+Y redoes (Cmd instead of Ctrl on macOS). Discard draft restores the catalog translation. Entries the language pack supplies, such as the naming keyboard rows, are read-only.

The check

The check runs after each change. It is the toolkit's per-entry check, the code its command-line batch check runs, executed in the browser with Pyodide: exact with the ROM, approximate without it. Without English the token and layout checks use the tracked snapshot, while typography and glossary checks that need English are explicitly unavailable.

Line meters

One meter per line, grouped by box, labelled with the width against the limit:

LabelMeaning
w / limit pxThe line fits; a meter past the wrap target marks a line longer than the preferred wrap width.
fits: shadow clipped1 px over, and the cut column of the last glyph holds only shadow: the line fits.
n px overThe line is wider than the window.
not encodableA character has no byte in the character map.

The meters show each line’s width against its visible limit and the number of lines against the window’s limit. Character and byte limits appear where they apply. Keyboard rows count keys.

Problems

Errors and warnings as the command-line check reports them, among them:

  • characters the language cannot encode;
  • placeholders or control codes that differ from the English;
  • lines wider than the window, or more lines than it shows, also in the windows of other font styles and on a sprite font's canvas;
  • a pair too wide for its line, naming the partner and a species that shows them;
  • written breaks the layout does not use because a line is too wide (warning);
  • a box that wraps to more lines than the English box (warning);
  • the typography rules of the language;
  • a glossary term of the English whose translation is not found (warning);
  • an empty translation of a non-empty English (warning).

A problem against an unmeasured limit ends in [unmeasured limit: the English width], one against an unverified estimate in [unverified limit: an estimate for this language].

In the game

With a ROM, English and translation are drawn in the original game font at the window's size, in the speaker's text colour where recorded, at 1×, 2× or 3×. Without a ROM only the translation appears, with stand-ins for ROM glyphs. The part of a line the game cuts is marked and its width shown, and a note names the line and the fix. When a written line is wider than its window, the layout may wrap the box anew without the written breaks; a warning names the line, and the meters and preview show the layout the build uses.

Until the check is loaded the page estimates the widths itself and reports no problems. At catalog stage the check covers tokens only (placeholders and control codes kept, braces matched, no control characters), and the preview shows the text without the game font. Game-catalog pull requests run the same checks with the project's quality gate (see Checks and review).

Drafts and export

Every change is a draft, kept in the local storage of the browser per game and language. Drafts survive a reload; they are not shared between browsers or devices, and clearing the data of the site deletes them. Where the browser refuses storage, drafts last only while the page is open. A text changed back to the catalog translation is no longer a draft.

After a site update, a page that stayed open may show The site was updated. Reload this page to continue. with the button Reload. The drafts are kept across the reload; the ROM is chosen again.

Export downloads every draft of the open game and language as one file, gen3tl-<language>-edits-<YYYYMMDDHHMM>.json (time in UTC). Exporting keeps the drafts.

KeyContent
language, profileThe language code and the game id.
entries[{id, translation, note}]: the changed texts.
pictures[{id, base, areas, tiles, png}]: kept uploads in area form; base identifies the project picture the edit was made on and png is base64 (see Pictures).
terms[{id, english, base, changes, include}]: term edits in glossary columns; base holds the values the edit was made on, changes the new ones, include the form-only entries the rename covers.
glyphs[{style, char or slot, width, rows, base}]: glyphs redrawn in the Fonts view, named as the art file names them; rows holds the cell rows of the art (# ink, s shadow or outline, _ background), base the width and rows the redraw was made on, for a copied letter its source copy:<byte> (see Fonts).
keyboard{rows, pages, base}: changed naming or chat rows by pack row name, the new page order where changed, and the values the edits were made on.

The export holds texts, glossary values, pictures in area form, glyph art and keyboard edits; it holds no ROM file and no ROM colour.

Submitting

Submit opens the submit page: this browser's drafts against the values they were made on, text widths, and a field for reviewer notes. Open a GitHub issue with these changes fills the appropriate repository's issue form; a GitHub account is needed. Download JSON saves every draft and is the route to use when no submission repository is configured or when a change must be sent another way.

Submission kindIssue destination and content
Game texts, terms or picturesThe game repository. Texts, terms and pictures travel in the issue; any glyph or keyboard edits in the same mixed export travel only in its JSON file.
Pack-only glyphs or keyboardThe toolkit repository. An export with no game texts, terms or pictures carries the glyph redraws and keyboard records in the issue itself.
Site-interface textsThe toolkit repository. The issue carries the changed interface entries; no ROM is involved.

The issue

The game form Translation submission has three fields. The toolkit form has the first two:

FieldContent
Editor exportThe submission as JSON: changed texts with their base translations; term edits with their base glossary values; pictures with text areas, tile counts and base identities; pack-only glyph and keyboard records where applicable; reviewer notes. The page fills the field while the form link stays within 8000 characters.
Export fileFor a longer submission, the page downloads JSON and opens the form without the inline document; drag that file into this field.
PicturesFor a game picture submission, drag each downloaded area-form PNG, <id>.png, into this field before submitting the issue.

Checks and review

Opening or editing an issue runs automatic validation. Errors are reported on the issue, and invalid changes are not applied. A valid submission becomes a pull request with automatic checks.

A maintainer reviews the pull request and merges it after the required checks pass. After the merge a new translation has the status Translated and enters the next patch; a text that was Approved stays Approved (see Review and release).

The JSON file

Download JSON and Export save every draft. Import a game export into review with:

gen3tl web import <export>.json --source contributor

The catalog stays unchanged until the review batch passes.

From a working copy

Run the editor against a working copy with:

PYTHONPATH=src python3 -m gen3tl web server start --page editor --foreground --profile <game> --lang <code>

The local page offers Save drafts to write text drafts into the catalog for review.

Terms

The Terms view lists every glossary term with the entries whose English names it and those whose translation holds one of its forms, most used first. Filters: category; use (used by entries, unused, shortened in use, edited here); order by uses, by English or as in the glossary.

Editable fields: translation; label, the form of short fields, empty when it equals the translation; gender; sources; notes; and the inflected forms by case and number. Forms are written by hand: the page has no morphology library. Revert restores the glossary row.

A change of the translation, the label, the gender or a form is a rename: it replaces each whole-word form of the term in every translation that uses it with the form of the same case and number. A different glossary term whose name encloses that form is protected and needs its own explicit rename. A change of notes or sources alone changes no line. When the translation changes while forms keep the old text, the view lists those forms.

Check the change previews the rename as the term rename command of the toolkit reports it: every line the rename changes and every line whose inserted-word slot it widens, each checked as a text is, with approved lines and lines with findings listed apart. The preview needs the check, and its widths are approximate without the ROM.

The entries using a term carry marks: English, the English names the term; form, the translation holds a form; shortened, the label stands for the full form; no form, translated without a form of the term (a glossary warning); form only, a form appears where the English does not name the term. A form-only entry is renamed only when include in the rename is checked.

A term edit is a draft; Export and the submission issue carry it in terms. The project applies a record only while its base equals the current glossary row.

Families

The Families view shows related terms side by side: the terms of one category that share an English word, the moves of one move type and the moves of one move list of the game. Its marks are review hints: wording, hyphens, shortened labels and, for moves, whether the names grow with the power. Terms are edited in the Terms view.

Pictures

The Pictures view lists the graphics that carry text, with screen, English text, category (translate, optional or keep) and reason, filtered by category, edit status (edited in the project, uploaded here, not edited, no ROM source) and text. The list needs no ROM. The pixels come only from the user's ROM: the page extracts each graphic in the browser with the graphics extraction code of the toolkit.

With the ROM loaded the view shows the original sheet with its text areas, the project's edit laid over it as the build lays it, and the upload, at 1× to 4×, with the palette.

  1. Download original sheet: an indexed PNG with the palette of the ROM. Download edited sheet gives the project's edit or the upload over the sheet of the ROM.
  2. Change only the text pixels in an image editor; keep the dimensions and the palette.
  3. Enter the text areas as x,y,w,h in sheet pixels, separated by semicolons. Tiles stays empty for the original tile count; a larger count appends tiles after the last one, which needs evidence that the game loads them over unused memory, and not every graphic can grow.
  4. Upload edited sheet. The page checks it as the pixel check of the toolkit does and lists the findings: a pixel changed outside the text areas, a change of dimensions or palette, a colour outside the palette, a change past the last tile.
ResultMeaning
Kept: included in the export.The sheet passes and differs from the original and from the project's edit.
Not kept: the sheet fails the check.See the findings.
Not kept: no pixel differs from the original.Nothing to keep.
Not kept: the sheet equals the project's edit.Nothing to keep.

A kept upload is stored in area form: an indexed PNG of the size of the sheet that holds the palette indices inside the text areas and the appended tiles, index 0 elsewhere, and a grey palette with no ROM colour. Remove upload deletes it. The downloaded sheets are built from the ROM and stay on the contributor's machine. Submit downloads the area form as <id>.png for the issue (see The issue).

Keyboards

The Keyboards view shows the pages of the naming screen keyboard that the language pack declares, in the order Select cycles through them from the page the screen opens on. The rows come from the pack's keyboard file, and the catalog holds them as read-only entries.

  • Screen preview: the key window of the page with every row at its pixel position, the frame in the colour of the page's look. With the ROM loaded every glyph is the game's; colours approximate the palette.
  • Keys: one cell per key, row by row: the glyph printed at that place, the character the key enters and its code, the x position and the 8-pixel tile in the key window, and the glyph's source (a language pack glyph, a copy of a base glyph, a base font glyph, or none). Keys outside the columns the cursor reaches are dimmed; a key without a glyph, a key printed as another character, a key that is not printed and a glyph outside the cursor frame of its column are marked. The game places the cursor from the column table of the ROM: the frame of a column spans 12 pixels from the column's x plus 8 in the key window.
  • Page label: the page's name on the page-swap button, which shows it while the page before it is open: the project's translated graphic where one exists, else the ROM's, drawn from your ROM as the Pictures view draws it. The game has one label per look, so pages of the same look share it; the graphic's id opens it in Pictures.
  • Page order lists the cycle, Page the keyboard, its base keyboard and look, the column count, the x of each cursor column and the page Select leads to, and Catalog rows the entries of the keys and of the printed rows, which open in the Texts view.

A page marked base ROM keys shows the keys of the original game; the other pages show the rows the build writes.

To change a key of the language pack, select it in Keys, type the character and choose Apply: the key enters the character and the printed row places its glyph in the middle of the key's cursor frame, the keys around it keeping their places. The arrows of Page order move a page in the Select cycle. The preview, the marks and the page list follow every change. The changes stay in this browser like text drafts, count in Export, travel as keyboard and are written to the pack's keyboard file by gen3tl web import; Discard keyboard changes drops them. A mixed game issue excludes them; a pack-only issue includes them (see Submitting).

Union Room chat

Where declared, Union Room chat follows the naming pages. The current Unbound data has three chat pages (uppercase, lowercase and symbols), ten rows each. Every row holds exactly five keys, including spaces; extended keyboard symbols are supported. The row shows its key count, pixel width against the row limit and encoded bytes against its slot capacity, with a preview. Apply accepts only a row that meets all three limits and whose keys are encodable; an invalid row reports its fit error and does not replace the last accepted draft. Chat edits join the other keyboard records in Export and JSON import.

Fonts

The Fonts view lists every glyph sheet the translation installs: each font of the profile (the font ids that select it, its glyph and width tables) and each sprite font, whose routine draws one tile per text byte through a byte-to-tile table. The art file of the language pack is linked; a glyph the pack draws can be redrawn in the view.

  • Sample: an editable text drawn in the sheet, by default the characters of the language pack. A sprite font draws every byte through its table, so a byte without a tile shows the fallback tile as the game does.
  • Tile sheet: for a sprite font, every tile in sheet order, 16 to a row: the ROM's tiles, then one tile for each letter the pack draws, framed. gen3tl lang sprite-sheet writes the same image as a PNG.
  • Glyphs: one cell per glyph with its character, code (hexadecimal), tile number and width; a red line marks the width or the advance. Cells the language pack adds, copies from another glyph or redraws are marked; with your ROM loaded, a glyph the pack redraws shows the original of your ROM beside it. The filter shows every glyph with a character, the pack's glyphs only, or every tile of the sheet in sheet order.
  • Redraw the glyph: clicking a glyph the pack draws opens a pixel grid at the cell size of the sheet. With your ROM loaded, a letter the pack copies from a ROM glyph opens too, drawn as the glyph it copies; redrawn, it becomes a letter of its own, which needs a drawing in every font style, so the view names the other sheets that still copy it. The palette holds ink, shadow and background, for a sprite font ink, outline and transparent with their palette indices; the width sets the columns of the art. Pixels outside the cell rows of the style and beyond the width stay dimmed. Every stroke updates the sample, the glyph's cell and the tile sheet, and is kept as a draft of this browser like a text edit; Export carries it in glyphs. Discarding the redraw returns to the pack's art. Before any import, the Texts view draws and measures the redrawn glyph at its new width in its previews, meters and check, the steps of a sprite font included, and the submit page measures the texts the same way.
  • Byte-to-tile table: for a sprite font, the tile drawn for each of the 256 byte values, the pack's entries marked.

Pokédex

The Pokédex is a read-only view of the game's published data in the selected language. Its names and descriptions resolve through that language's keyed catalog. Changing the site and game language keeps the open card and the page, list and detail scroll positions.

A move with variable power shows an explanatory formula paragraph. Where the data distinguishes conditions, a Condition / Power table lists the tiers; a compact move popup shows a dash for such a formula. These texts explain the implemented game behavior.

In a species' move table, a weight-based move's power is calculated against that target species' unmodified base weight. The cell tooltip, Power against this species at its base weight, states this basis; other move powers and their formula explanations remain unchanged.

Review and release

The checks of the editor cover fit and form; meaning is left to people. Every text has one of three statuses:

StatusMeaningIn a patch
UntranslatedNo translation yet.The game shows the original text.
TranslatedA maintainer merged the translation.Yes.
ApprovedThe text was part of a version whose playtest was reported, or it passed the review of the project.Yes.

Merging the pull request is the review of a contribution. A playtest of a released version is reported with the Playtest report form of the game project; the translated texts that have not changed since that version then become approved. A later edit of an approved text stays approved.

For the languages the project maintains itself, texts are grouped into batches by origin (one map's scripts, one battle text table, one description table), each batch with its context, and every batch passes three review passes, each independent of the translation it checks:

PassWhat it checks
AccuracyMeaning against the English and the context; glossary terms; character and place names; the gender of speaker and addressee; placeholders and control codes.
ProofreadingSpelling, grammar, punctuation and typography by the norms of the written standard language.
EditorialRegister and character voice; the form of address per speaker as the glossary records it; tone matching the original; consistency with approved batches.

Every finding goes back to the translation, and the affected pass is repeated. A batch is approved when all three passes report no findings. Sweeps over all approved batches repeat the proofreading and editorial passes after every few batches and before a release. Before every build the quality gate checks that placeholders and control codes are preserved and only encodable characters are used, the layout fit, the glossary usage and the consistency of identical source strings. Translated and approved texts enter the next release of the translation patch.

What a translation keeps

  • The meaning of the English in its context: speaker, addressee, map and neighbouring lines.
  • Glossary terms and names as the glossary records them.
  • Every placeholder and control code of the English, except those the rules of the entry allow to drop.
  • The fixed form of an inserted word: the sentence is built around it.
  • Text addressed to the player avoids forms that mark the player's gender: the player character can be of either gender.
  • Consistency with the approved translations of the same English, which the context pane lists.
